Why 100 of the 101 mined outputs are unspendable

Each of the 101 blocks has a coinbase transaction paying the 50 BTC subsidy to my mining address, so 101 outputs worth 5 050 BTC exist. Consensus forbids spending a coinbase output until it has 100 confirmations on top of it (COINBASE_MATURITY). At height 101 only the block-1 coinbase satisfies this (it has 101 confirmations); the coinbases of blocks 2–101 have between 100 and 1 confirmations and are immature. The rule exists because a chain reorganisation removes the coinbase of an orphaned block: without a maturity delay, coins that later vanish could already have been spent onward, and every descendant transaction would become invalid.

The wallet and the node look at the same data from two angles. listunspent lists only outputs the wallet can spend now, and never includes immature coinbase outputs, which is why it shows one entry; getbalances reports the other 100 × 50 = 5 000 BTC under immature. gettxoutsetinfo is the node's view of the whole UTXO set, independent of any wallet: it counts every unspent output regardless of owner or maturity, hence 101 outputs and 5 050 BTC. Both views agree that 101 coinbase outputs of 50 BTC exist and one is mature. The count is 101 and not 202 because each regtest coinbase also has a zero-value OP_RETURN witness-commitment output, which is provably unspendable and therefore never added to the UTXO set.

This also shows that a balance is a derived quantity: 50 BTC is the sum the wallet computes over its spendable UTXOs; no account balance is stored anywhere in the protocol.

Amount computation (B3)

My input is 50 BTC, I send 10 BTC, and I chose a fee of 0.0001 BTC (10 000 sat). The fee is not written anywhere — it is whatever the outputs leave unclaimed — so the change output must absorb the rest:

change = 50 − 10 − 0.0001 = 39.9999 BTC  →  fee = Σinputs − Σoutputs = 50 − (10 + 39.9999) = 0.0001 BTC

createrawtransaction serialised one input and two outputs {dest: 10.0}, {change: 39.9999}; it performs no check of amounts against the input. signrawtransactionwithwallet returned "complete": true and a signed hex of 444 hex characters (222 bytes).

Where the two representations differ

The hashes. The node labels the witness hash hash; my parser calls it wtxid. Both are double-SHA-256 values, but over different bytes: the txid is computed over the legacy serialisation without marker, flag and witness (113 bytes), the wtxid over the full 222 bytes. Because this is a SegWit transaction, they differ; for a legacy transaction they would be equal (tested on the genesis and block-170 transactions).

Byte order. Every hash is stored little-endian but displayed big-endian. The previous txid appears in the raw bytes at offset 7 as 9f5bc19f64e17039…b0fca44a3b, which is the byte-reversed form of the displayed 3b4aa4fcb007fa26…649fc15b9f. I apply the same reversal to the computed txid and wtxid before printing; without it, neither would match the node.

Notation. The node prints the sequence in decimal (4294967293), amounts in BTC, OP_0 as 0 and uses Core's type names; my parser prints hex, satoshis, full opcode mnemonics and the lab's short type names. The underlying values are identical.

Result: my parser's txid equals the one returned by sendrawtransaction, and its wtxid equals the node's hash — for Part B and also for the Part D transaction (1e083cb6…3f5a3ba3 / c75065b9…82917f2a).

4. Part D — the deliberate mistake

I repeated Part B with the now-mature block-2 coinbase (66477223…b4b86ea5:0, 50 BTC) but with a single output of 10 BTC to bcrt1qmm4drjz0…flhjwq and no change output.

The first refusal is not a consensus rule. It is a safety limit in Bitcoin Core's RPC (maxfeerate, default 0.10 BTC/kvB). This transaction pays 40 BTC for 110 vB — about 36 million sat/vB, roughly 500 000 times the 71 sat/vB of Part B — so the RPC refuses it. When I passed 0 to disable the check, the network accepted the transaction.

Who received the 40 BTC

The miner of block 103 — whoever was paid by that block's coinbase. The coinbase claims 90 BTC = 50 BTC subsidy + 40 BTC fee, paid to the address given to -generate, which is in my own wallet. The coins therefore return to me as an immature coinbase: after block 103, getbalances shows immature 5040.0001 BTC (100 × 50 + 40 + 0.0001, the last two being the Part D and Part B fees) and trusted 109.9999 BTC (3 mature coinbases × 50 − 40 − 0.0001). On mainnet the miner is an unrelated party and the 40 BTC would be lost.

Why the transaction was consensus-valid

Consensus checks value with two inequalities: for each transaction Σinputs ≥ Σoutputs (50 ≥ 10), and for each block the coinbase may claim no more than subsidy + Σfees (90 ≤ 50 + 40). Both hold. Nothing in consensus limits how large the difference may be, because the protocol cannot know whether a large remainder is a mistake or an intentional payment to the miner. The signature committed to exactly these outputs, so the transaction is valid as signed.

Why Ethereum's account model makes this error impossible

Ethereum's state is a mapping from accounts to balances, and a transaction is a state transition rather than the consumption of whole outputs. For a simple transfer the transition function does balance[sender] −= value + gas_used × gas_price and balance[recipient] += value. The sender states only the amount to move; everything not moved simply stays in the sender's account. There is no set of outputs that must be balanced against the inputs, so there is no remainder that can be forgotten. The fee is not implicit either: it is derived from explicit, signed fields and bounded in advance by gasLimit × maxFeePerGas (unused gas is refunded), so the sender can never pay more than that cap. In Bitcoin's UTXO model an input is consumed whole and anything not re-assigned to an output becomes the fee; in Ethereum, anything not transferred remains the sender's balance.

5. Why Bitcoin has no explicit fee field

Bitcoin transactions carry no fee field because the fee is already fully determined by data the network holds. Every input points to an earlier output, and that output's value is fixed in the UTXO set; the transaction cannot change it. Every validating node therefore knows the sum of the inputs and reads the sum of the outputs, so fee = Σinputs − Σoutputs follows without any extra information. An explicit field would be redundant, and worse, it could contradict the implicit value. The protocol would then need one more consensus rule to say which number wins.

The design buys simplicity in several places. Validation of value is a single inequality per transaction: Σinputs ≥ Σoutputs. The miner's reward needs no fee bookkeeping either: the coinbase may claim the block subsidy plus the sum of all remainders, which Part D showed as 50 + 40 = 90 BTC. Pricing is left entirely to the sender, who sets the fee rate (sat/vB) through the size of the remainder; a fee market emerges without the protocol fixing any price. Finally, every transaction is a few bytes smaller.

The cost is that the fee is invisible and easy to get wrong. A sender who forgets the change output does not get an error from consensus; the transaction is valid, and the whole remainder goes to the miner, exactly as in Part D, where 40 BTC was lost to a fee. The fee also cannot be read from the transaction alone: my Part C parser has to refuse to print it, because the input values live in other transactions. This is why wallets and Bitcoin Core add guard rails outside consensus, such as the maxfeerate check that rejected Part D with error −25.
